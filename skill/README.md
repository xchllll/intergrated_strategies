## 一、工程环境与工具链

## 技能1：Git 强制走代理与网络超时（443端口）排错

- **适用场景**：在 Windows 环境下使用 VS Code 终端 `git push` 时，频繁报错 `Failed to connect to github.com port 443 after 21000 ms: Could not connect to server`。
- **踩坑清单**：
  1. **系统代理与 Git 脱节**：在 CMD 运行 `netsh winhttp show proxy` 显示“直接访问”，但这仅代表 Windows 系统服务没走代理。Git 默认是独立的，不会自动吃浏览器的代理。
  2. **找对代理端口**：打开代理软件（如 SakuraCat），找到“Mixed 端口”（如 `127.0.0.1:12450`），该端口通常兼容 HTTP 和 SOCKS5。
  3. **配置 Git 代理**：在终端执行：
     `git config --global http.proxy http://127.0.0.1:12450`
     `git config --global https.proxy http://127.0.0.1:12450`
- **验证方法**：执行 `git config --global --get http.proxy` 检查是否生效，再次 `push` 成功即说明解决。

## 技能2：Windows 环境下 Git 权限与代理一键配置

- **适用场景**：使用 VS Code 或命令行推送代码到 GitHub 时，频繁提示 `not found`、`Permission denied` 或网络超时。
- **踩坑清单**：
  1. **网络超时**：Git 默认不走系统代理。需在终端执行 `git config --global http.proxy http://127.0.0.1:<你的加速器端口>`。
  2. **权限不足**：去 Windows 的“凭据管理器” -> “Windows 凭据”中，删除所有以 `git:https://github.com` 开头的记录，强制 Git 重新弹窗授权。
- **验证方法**：在终端运行 `git push`，看到 `Everything up-to-date` 或进度条满即可。

## 技能3：VS Code 虚拟环境 (venv) 冲突与真伪验证

- **适用场景**：在 VS Code 中新建文件夹并配置 Python 环境时，系统提示“已将包安装到全局环境中”，或不确定依赖是否装入了虚拟环境。
- **使用方法 / 踩坑清单**：
  1. **忽略假警报**：若终端命令行前缀已出现绿色的 `(.venv)`，但 VS Code 右下角仍弹窗提示“建议创建虚拟环境”，直接点“不再显示”。这是 VS Code 的 Python 插件界面未及时同步导致的。
  2. **终极验证法**：在激活状态下，终端输入 `where pip`。如果第一条路径是 `...\.venv\Scripts\pip.exe`，说明包百分之百装在了隔离环境中。
  3. **选择解释器**：按 `Ctrl+Shift+P` 打开命令面板，输入 `Python: Select Interpreter`，手动指定路径包含 `.venv` 的那个 Python 解释器，可彻底消除警告。
- **失效条件**：若在虚拟环境中 `pip install` 成功，但运行代码依然报 `ModuleNotFoundError`，说明当前终端运行的并非 `.venv` 里的 Python，需检查并重新激活。

## 技能4：Python/Vivado 多环境与字符编码排雷指南

- **适用场景**：使用 VS Code 编写和运行 Python 脚本，或在 Vivado 中跑 Testbench 仿真时，遇到依赖库找不到、标点报错、乱码或死循环。
- **使用方法 / 踩坑清单**：
  1. **Python 模块找不到**：若 `pip install` 成功但 VS Code 报 `ModuleNotFoundError`，说明遇到了多环境冲突。在终端运行 `python -m pip install <模块名>` 强制给当前运行的 Python 安装。
  2. **代码带框/报错**：AI 生成的代码常带有中文全角逗号或不可见字符，VS Code 会高亮提示。复制后务必检查并替换为英文半角符号。
  3. **Vivado 仿真乱码**：Verilog 的 `$display` 尽量不要输出中文，防止 UTF-8 与系统 GBK 编码冲突。
  4. **Vivado 仿真死循环**：若修改了代码加了 `$finish` 仍不停，且提示 `Invalid Top Module`，说明新代码编译失败，Vivado 加载了旧快照。使用 `Flow -> Reset Behavioral Simulation` 清理缓存后重跑。

## 技能5：Python 跨目录文件路径锚定法

- **适用场景**：运行脚本时（如 `python train.py`），无论终端在哪个目录下，脚本都找不到相对路径的 `data/` 或 `model/` 文件夹。
- **使用方法 / 踩坑清单**：
  1. **废弃相对路径**：绝对不要用 `../data/` 这种依赖当前终端位置的相对路径。
  2. **路径锚定**：使用 `pathlib` 获取当前文件的绝对路径并向上回溯，如 `ROOT_DIR = Path(__file__).resolve().parents[2]`，再拼上 `ROOT_DIR / "data" / "file.csv"`。
- **验证方法**：在任何一个嵌套目录下执行脚本，路径均不会报 `FileNotFoundError`。

## 技能6：跨平台环境自适应与代码优雅降级

- **适用场景**：同一套上位机（网页+算法）代码，既要能在 Windows 电脑上无硬件演示（读 CSV），又要在 PYNQ 上跑真实硬件。
- **使用方法 / 踩坑清单**：
  1. **自动识别**：在 `app.py` 中引入 `platform.system()`。Windows 下自动读本地 CSV；Linux（PYNQ）下自动调 T1 的 `ps_ctrl` 等硬件模块。
  2. **防崩溃保护**：在使用 `import` 引入硬件驱动时，务必包一层 `try-except` 或基于环境判断，防止在电脑上因无 `pynq` 库直接崩溃红字。
- **验证方法**：在电脑上跑，网页显示“演示数据”；原样拷到板子跑，网页显示“实测数据”，一套代码两地开花。

## 技能7：Vivado 波形显示排错指南

- **适用场景**：在 Vivado 中跑仿真时，数字信号（如正弦波、PID输出）波形显示异常（如折叠、全是方块）。
- **使用方法**：
  1. 若输出为负数（有符号数据），右键信号名 -> `Radix` -> 选择 `Signed Decimal`。
  2. 若要观察模拟包络线，右键信号名 -> `Waveform Style` -> 选择 `Analog`。
- **失效条件**：此方法仅改变仿真视图的显示方式，不改变底层硬件数据。若修改后波形仍杂乱，需排查 RTL 代码中是否发生了位宽溢出。

## 技能8：Vivado 仿真环境排雷与波形调试技巧

- **适用场景**：在使用 Vivado 进行 RTL 行为级仿真时，遇到环境报错、找不到信号、或波形显示异常。
- **使用方法 / 踩坑清单**：
  1. **旧进程占用（文件无法访问）**：如果点击 Run Simulation 报错 `另一个程序正在使用此文件`（如 `simulate.log`），说明上一次仿真的后台进程（`xsimk.exe`）未退出。解决办法：在 Vivado 中点击 `Flow -> Close Simulation`，或去 Windows 任务管理器结束 `xsimk.exe`。
  2. **找不到内部模块信号**：在波形窗口试图添加 `state` 或 `shift_reg` 等内部信号时，若在顶层 `tb` 找不到，必须在左侧的 `Scope` 窗口双击实例化的 `dut`（被测模块），进入其内部层级后，才能在 `Objects` 窗口选中并拖入波形。
  3. **仿真乱码**：Testbench 中的 `$display` 或 `$fwrite` 尽量只输出纯英文和数字。中文字符极易与 Windows 系统的 GBK 编码冲突导致乱码，且不影响波形本身的正确性。
  4. **幽灵缓存（代码更新但仿真结果不变）**：若确信代码已保存，但跑出的波形/数据依然是旧的，通常是 Vivado 读取了旧的编译缓存。解决：`Flow -> Reset Behavioral Simulation`，或直接关闭 Vivado，手动删除工程目录下的 `*.sim` 文件夹后重新打开。
  5. **仿真死循环/无法停止**：如果跑仿真时进度条一直卡住不停，检查 Testbench 中是否漏写了 `$finish`，或者 `for` 循环的边界条件写死导致出不来。按下仿真窗口上方的红色正方形（Stop）强制中断即可。
- **失效条件**：此技能仅适用于仿真阶段的软件排错。如果上板（Bitstream）后硬件逻辑不对，应使用 ILA（集成逻辑分析仪）进行在线抓取波形，而非仿真。

## 技能9：Matplotlib 混淆矩阵中文变方块修复

- **适用场景**：在 Linux (PYNQ) 或无中文字体配置的环境中，使用 `matplotlib` 生成带中文标签的混淆矩阵图。
- **使用方法 / 踩坑清单**：
  1. **字体配置**：必须在导入 `matplotlib.pyplot` 之前，强制指定后备字体并修复负号显示。

## 二、RTL / FPGA 设计

## 技能10：Verilog 三段式状态机（FSM）设计规范与排雷

- **适用场景**：在 FPGA 中设计控制流程（如扫频控制、接口通信时序、按键消抖等）。
- **使用方法 / 设计规范**：
  1. **严格使用三段式**：
     - 第一段（时序逻辑 `always @(posedge clk)`）：仅负责当前状态 `state <= next_state`。
     - 第二段（组合逻辑 `always @(*)`）：使用阻塞赋值 `=`，根据当前状态和输入信号算出 `next_state`。**绝对不能用时序逻辑写第二段**，否则每个状态会多停留一个时钟周期。
     - 第三段（时序逻辑）：根据当前 `state` 输出控制信号（如 `clear`、`en`）。
  2. **单周期脉冲防叠加**：在第三段 `always` 块开头，必须默认将输出信号赋值为 0，再在 `case` 分支里拉高，确保输出的是干净的单周期脉冲，防止下游模块一直处于复位状态。
  3. **位宽防呆（钳位）**：在状态机变量计数时（如 `freq_idx`），即使位宽足够（如 8位最大 255，扫 240 个点），也务必加上 `if (cnt < MAX)` 的限制，防止状态机跑飞导致异常回绕。

## 技能11：I2S 协议发送模块（Master TX）标准实现

- **适用场景**：需要用 FPGA 向音频 DAC/Codec 芯片发送串行音频数据时。
- **核心设计规范**：
  1. **动态声道选择**：使用 `wire [15:0] active_audio = lrclk ? audio_data_L : audio_data_R;`，避免复杂的逻辑分支。
  2. **错峰更新**：通过 `bclk_fall_d` 将数据更新延迟到 `bclk` 下降沿之后的系统时钟周期，绝对避免建立/保持时间冲突。
  3. **高位寻址**：使用 `case` 语句直接通过 `bit_index` 索引 `active_audio[15-bit_index]`，绝不使用易错的移位寄存器。
- **验证方法（Self-Checking Testbench）**：在测试台中不要只看波形！在 `posedge bclk` 处，利用内部变量（如 `slot_index`）自动推算出 `expected_sdata`，并与真实的 `sdata` 比对，一旦出错立即通过 `$display` 打印 ERROR。这种验证方式在大型工程中极其高效。

## 技能12：I2S 协议接收（RX）模块 RTL 设计规范

- **适用场景**：FPGA 作为 I2S Master，需要从音频芯片（如 ADAU1761）或外部 ADC 采集串行数字音频信号时。
- **核心设计规范**：
  1. **时钟边沿检测**：因为 FPGA 是 Master，`bclk` 是由内部 100MHz 分频产生的。不用跨时钟域，直接用 `clk` 打两拍检测 `bclk` 的上升沿（`bclk_rising`）。
  2. **延迟采样与移位**：在 `bclk_rising` 脉冲到来时，将 `sdata_in` 放入移位寄存器的最低位，并左移。在 `bit_cnt == 16` 时，根据 `lrclk` 的高低电平，将 16 位移位寄存器的数据锁存到左声道或右声道。
  3. **MCLK 必须提供**：绝大多数音频 Codec 芯片（如 ADAU1761）在进入 I2S 模式前，必须有主时钟（MCLK，通常约 12.288MHz）驱动。RTL 中可通过简单的分频（如 100MHz/8 = 12.5MHz）生成并绑定到特定物理引脚（PYNQ-Z2 为 U5）。
- **失效条件**：若 `bclk` 由外部提供，需改为跨时钟域处理；若 MCLK 缺失，芯片将静音，导致采回的数据全是底噪。

- **常见排错（Vivado 专属）**：
  1. **旧进程占用**：仿真报错 `另一个程序正在使用此文件`，需点击 `Flow -> Close Simulation` 关闭旧的波形窗口，或去任务管理器杀掉 `xsimk.exe`。
  2. **找不到内部信号**：在波形窗口加信号时，若找不到 `state`，需在左侧 `Scope` 窗口双击底层的 `dut` 实例才能看到内部变量。
  3. **仿真太慢**：将 `TIME_MAX` 计时参数改小（如 10000 改为 5），以加速仿真。
- **失效条件**：如果在组合逻辑段（第二段）中使用了 `<=`，或在时序逻辑段（第一、三段）中使用了 `=`，将导致综合出的硬件存在竞争冒险或毛刺。

## 技能13：正交解调（I/Q Demodulation）定点化设计规范

- **适用场景**：在 FPGA 内进行交流信号（如正弦波）的幅值与相位测量，且仅有 16 位 ADC 采样精度时。
- **使用方法**：
  1. **混频（乘法）**：16位 ADC 信号与 16位本振（DDS生成的cos/sin）相乘，结果需用 32 位寄存器存储，防止溢出。
  2. **积分累加**：积分窗口为 N 个点时，需预估最大值。例如 15000 * 32767 * 1000 ≈ 4.9e11，需使用 **48位** 累加器（`reg signed [47:0]`）。
  3. **归一化**：计算最终幅度前，需将累加结果除以（N * 放大倍数）还原真实值。
- **失效条件**：若累加器位宽不足 48 位，长时间积分会导致数据高位溢出翻转，波形与计算完全错误。


## 三、音频 Codec 与链路

## 技能14：I2S 数据线方向核对（sdata_o / sdata_i 绝不能对调）

- **适用场景**：FPGA 作为 I2S Master 与 Codec（ADAU1761 等）对接，通路能"跑通"但采回的数据是错位/无意义的，或示波器上看到数据在动、解码却失败。
- **使用方法 / 踩坑清单**：
  1. **以"方向"而不是"引脚号"命名**：约束里必须写清 `sdata_o`（FPGA→Codec）和 `sdata_i`（Codec→FPGA）。只写 `sdata_0/sdata_in_0` 这类中性名字，一旦有人在 XDC 里调换顺序，RTL 与约束会同时"自洽"，问题极难发现。
  2. **PYNQ-Z2 + ADAU1761 的正确引脚**：`MCLK=U5`、`BCLK=R18`、`LRCLK=T17`、`sdata_o(FPGA→Codec)=G18`、`sdata_i(Codec→FPGA)=F17`。其它引脚（如 `sdata` 与 `sdata_in` 互换）会在电平上"看起来正常"，但数据是错位的。
  3. **优先级高于猜"主从模式"**：Codec 被配成 master 时通常表现为时钟完全缺失、数据全 0；而**数据线接反**表现为时钟正常、累加器有小幅但不随频率变化的读数——两者症状不同，先分辨再动手。
- **失效条件**：若 Codec 是被配置为 Master（由 Codec 提供 BCLK/LRCLK），则 FPGA 侧接收应改为跨时钟域处理，本条的"方向核对"思路仍然成立，但引脚表需按实际板卡重查。

## 技能15：I2C 寄存器回读的正确姿势（repeated start）

- **适用场景**：需要通过 I2C 读回 Codec 寄存器值做验证（如确认某个位真的写进去了）。
- **使用方法 / 踩坑清单**：
  1. **`os.write` + `os.read` 分两次调用不可靠**：Linux 的 i2c-dev 在两次调用之间会发 STOP，很多 Codec 会因此复位内部地址指针，读回的是**写入缓冲区里的内容**（看起来"读到了"，其实是回声）。
  2. **必须用 `I2C_RDWR` 组合消息**：一次 ioctl 内完成"写寄存器地址 + repeated start + 读数据"，才是真正的寄存器读。
  3. **因此"读回等于预期"不能作为写成功的证据**：尤其 PLL 锁定这类判断，回读只是配置镜像。要证明硬件真的生效，必须看**行为**（数据是否在变、时钟是否存在、耳机是否有声）。
- **失效条件**：若 Codec 支持寄存器读且驱动已正确实现 repeated start，则回读可信；但对"状态类"字段（锁定、就绪）仍建议用行为验证。

## 技能16：Codec 静音三连查（HP 音量 / DAC 到混音器 / 电源管理）

- **适用场景**：时钟已正常、I2C 写入也成功，但耳机里始终没有声音。
- **使用方法 / 踩坑清单**：
  1. **耳机音量寄存器带静音位**：`PLAY_HP_LEFT/RIGHT_VOL(0x4023/0x4024)` 的 **bit1 是 mute 开关**。`0xE5` 表示"音量为 0 且静音"，写 `0xE7` 才是解除静音。
  2. **DAC 到混音器的开关默认是关的**：`PLAY_MIXER_LEFT0(0x401C)` 的 **bit5**、`PLAY_MIXER_RIGHT0(0x401E)` 的 **bit6** 必须置 1（常见值 `0x21` / `0x41`），否则 DAC 输出根本进不了耳机放大器。
  3. **电源管理也要开**：`PLAY_POWER_MGMT(0x4029)` 与 `DAC_CONTROL0(0x402A)` 需要使能对应通道，否则前述寄存器写了也没用。
  4. **排查顺序**：先写"电源管理 + DAC 控制"，再写"混音器开关"，最后写"音量"。顺序反了会误判为"寄存器写进去了但没反应"。
- **失效条件**：若通路里串了外部功放或继电器，还需检查外部使能信号；上述寄存器只覆盖 Codec 内部链路。

## 技能17：音频通路的"分层验证法"

- **适用场景**：一条"数字 → 模拟 → 数字"的闭环通路出问题，现象混杂（没声音、数据不动、曲线乱跳），不宜直接猜某个模块坏了。
- **使用方法 / 踩坑清单**：
  1. **第一层：数据在不在动**——绕开校准与显示层，直接读最底层的累加器（48 位 `acc_I/acc_Q`）。若读数几乎不变、且幅值贴着满量程的直流量（如恒为 0xFFFF/0x0000），说明**根本没有信号进来**，后面所有"相位/幅值分析"都无意义。
  2. **第二层：时钟对不对**——核算 `MCLK / CONVSR / LRCLK`（见技能十九），并确认 MCLK 引脚上确有波形。
  3. **第三层：模拟开关开没开**——HP 静音位、混音器开关、电源管理（见技能十八）。
  4. **第四层：引脚映射对不对**——数据线方向、I2C 引脚（见技能十六、技能十三）。
  5. **最快的分层工具：直接放一个单音**。绕开扫频状态机，直接写 DDS 频率寄存器输出 1 kHz 到耳机——能听到就证明"数字→模拟"整条链路是通的，问题一定在"模拟→数字"或测量逻辑侧。
- **失效条件**：若通路中不含模拟环节（纯数字环回），则第三层不适用，直接从第一、二、四层排查。

## 技能18：MCLK / CONVSR / LRCLK 三者必须自洽

- **适用场景**：低频段测量正常、高频段重复性骤降或幅值异常，怀疑数字音频链路有问题。
- **使用方法 / 踩坑清单**：
  1. **先算一遍三个数**：`fs = MCLK / CONVSR`。ADAU1761 的 `CONVERTER0(0x4017)` 中 `CONVSR[2:0]`：`0 → 1024×fs`、`6 → 512×fs`。
  2. **fs 与 LRCLK 必须相等**：LRCLK 是 I2S 帧率（本项目 100 MHz / 2048 = 48.828 kHz）。若 `MCLK/CONVSR ≠ fs_LRCLK`，Codec 内部会按错误的采样率转换，表现为**高频混叠**——低频看着正常、高频重复性极差（实测 cv 可达 64%）。
  3. **反例与修正**：MCLK = 10 MHz + CONVSR = 1024 → fs = 9.77 kHz（差 5 倍）；改为 MCLK = 25 MHz（100 MHz/4）+ CONVSR = 512 → fs = 48.828 kHz，与 LRCLK 严格相等。
  4. **验证方法**：对同一频点重复测 8~10 次算 cv。混叠区的 cv 会明显高于低频段；修好之后各频点 cv 应落在同一量级。
- **失效条件**：若 MCLK 由外部晶振提供而非 FPGA 分频，则"MCLK 可调"这条不成立，只能通过改 CONVSR 或改 LRCLK 分频来对齐。

## 技能19：ADAU1761 时钟模式——PLL 锁不上就走 MCLK 直通

- **适用场景**：通过 I2C 配置 ADAU1761 后没有声音或没有采样数据，且 `config_audio_pll` 之类的流程超时。
- **使用方法 / 踩坑清单**：
  1. **先分清两个寄存器**：`CLOCK_CONTROL(0x4000)` 管核心时钟源，`PLL_CONTROL(0x4002)` 管 PLL 参数（6 字节突发写，volatile）。
  2. **PLL 锁定的"回读"可能是假象**：很多库的"检查锁定"只是把刚写进去的配置读回来比对，PLL 实际没锁也会通过。判定锁定必须依赖**外部时钟测量**（示波器/频率计）或**数据是否真的在流动**，不能只看寄存器。
  3. **PLL 不通就干脆旁路**：写 `0x4000 = 0x01`（SYSCLK_EN，核心时钟 = MCLK，PLL 旁路）。这也是 Linux 驱动在配置 PLL 之前的默认状态，稳定、可预测。
  4. **MCLK 必须由 FPGA 提供**：PYNQ-Z2 上 `au_mclk` 输出到 U5，没有 MCLK 时 Codec 完全不出数据。
- **失效条件**：若目标采样率无法由"MCLK / CONVSR"整数分频得到（例如需要 44.1 kHz 而 MCLK 只能整 MHz），就必须回到 PLL 方案，此时应先修好 PLL 再谈旁路。

## 技能20：PYNQ-Z2 板载音频 Codec (ADAU1761) I2C 通路排雷

- **适用场景**：在 PYNQ-Z2 上自定义 PL 硬件，通过 PS 的 I2C EMIO 引脚控制 ADAU1761 进行音频收发时。
- **核心避坑指南**：
  1. **引脚错位坑**：官方手册或网上部分教程会将 Arduino 扩展口的 `P15/P16` 误标为 Codec I2C。实际上 ADAU1761 的 I2C 引脚是 `U9 (SCL)` 和 `T9 (SDA)`。如果约束到 P15/P16，I2C 会一直报 `Errno 6 (NACK)`。
  2. **缺少 iic_bidir 导致静音**：自定义 BD 时，务必在 PL 端例化一个 `iic_bidir` 模块，将 PS7 的 `I2C1_*` 6 根引脚接入，再将 `scl_io` / `sda_io` 引出为外部端口，否则加载自定义 bitstream 后 Linux 会失去对 Codec 的硬件控制权。
  3. **时钟域锁死**：ADAU1761 必须配置 PLL 才能工作。通过 I2C 写入 PLL 参数后，必须回读 `0x4002` 寄存器确保锁定，再开启核心时钟（`0x4000` 写 `0x0F`）。
- **失效条件**：若 PL 端 `au_mclk` 没有正确输出 10MHz 方波，I2C 即使配置成功，PLL 也无法锁定，ADC/DAC 无法输出有效数据。


## 四、PS-PL 联调与 PYNQ

## 技能21：Python-PL 软硬联调的轮询时间规范

- **适用场景**：PS 侧通过 Python 操作 MMIO（如 AXI GPIO）控制 PL 状态机，并轮询 `done` 信号时。
- **核心设计规范**：
  1. **理论时间不可靠**：积分时长（如 `window_n / fs`）只是理论硬件执行时间。
  2. **开销补偿**：Python 的 `time.sleep()` 精度极差，单次 MMIO 读写也有几十微秒的延迟。`timeout` 必须给足裕量。例如，10ms 的硬件积分，超时阈值必须设为 50ms 甚至 100ms。
  3. **调试三板斧**：当 `measure_once` 超时时，不要先怀疑 RTL 代码。第一步用 `MMIO` 裸写寄存器拉高 `start`；第二步死等 50ms；第三步直接读取地址。如果裸测能读到 `done=1`，说明硬件没问题。
- **失效条件**：如果裸写 MMIO 且死等后 `done` 仍为 0，说明 RTL 状态机因缺少数据激励（如音频线未接）或时钟丢失而死锁。

## 技能22：双后端验收脚本 (acceptance.py) 的逻辑分离

- **适用场景**：同一个软件接口既要支持官方底层库（如 PYNQ AudioLoopback），又要支持自研 FPGA 链路时。
- **设计规范**：
  1. **字典字段差异**：音频 FFT 库返回的是 `amplitude_code` / `spectral_peak`，而自研链路返回的是 `acc_i` / `acc_q`。两者的字典 Key 完全不同。
  2. **判定分离**：在 `checks` 字典中，应该用 `if backend == "rtl": checks.update(...)` 来区分判定标准。
  3. **RTL 的验收底线**：自研 RTL 链路不依赖频谱峰值，只需满足：`done == True`、`abs(acc_i)+abs(acc_q) > 阈值`（防止纯底噪）、`clock_hz == 预期` 即可 `passed: true`。
- **失效条件**：强制用 FFT 的指标去校验时域 IQ 的输出，会导致“硬件明明通了，软件却判失败”的乌龙。

## 技能23：AXI GPIO 硬件映射取证与 PS 侧驱动编写规范

- **适用场景**：在 PYNQ / Zynq 上编写 Python 驱动控制 PL 侧 AXI GPIO 外设时，需要确切的基地址、通道位宽与信号连接关系，不能靠猜。
- **使用方法 / 踩坑清单**：
  1. **不猜地址**：Vivado 导出的 `.xsa` 本质是 zip 包。解压后读取 `design_1.hwh`（IP 端口连接表）和 `design_1.bda`（地址段映射）。在 `bda` 中搜 `SEG_<IP>_Reg` 可找到 `C_BASEADDR`（如 `0x41200000`）。
  2. **寄存器偏移固定**：axi_gpio 数据寄存器偏移为 ch1=0x00、ch2=0x08，TRI 方向为 0x04/0x0C；先核对参数 `C_GPIO_WIDTH` / `C_GPIO2_WIDTH`，位宽不足时高 16 位会被截断。
  3. **48 位有符号回读**：累加器拆成“低 32 位 + 高 16 位”两个通道拼接，再按补码符号扩展成 Python 负数（`v - (1<<48) if v >= (1<<47)`）。
  4. **时序清零陷阱**：PS 把 `start` 拉低后，状态机回 IDLE 会触发 `clear` 清零累加器——取数必须在 start 仍为高电平时完成，驱动里用“启动 → 等待 → 读数 → 停止”的便捷接口规避。
- **失效条件**：直接按“常见 0x40000000”猜基地址，地址错误时 AXI 写静默失败；未核对通道位宽直接读 48 位，得到的是截断/错位数据。

## 技能24：Zynq-7000 PS+PL (AXI GPIO) 软硬件联调排雷指南

- **适用场景**：使用 PYNQ 框架，通过 Python（PS侧）控制 PL 侧自定义 IP（RTL代码）的数据读写时。
- **使用方法 / 踩坑清单**：
  1. **外部复位陷阱**：如果在 `top.v` 中使用了外部 `rst_n` 输入，但在 Block Design 中悬空，会导致芯片永远处于复位状态。**强烈建议**：在 RTL 内部写一个上电自动复位计数器（如数 255 个周期后拉高 `sys_rst_n`），彻底抛弃外部复位，避免物理按键未接导致的死锁。
  2. **位宽匹配**：48 位或 64 位的超大寄存器，不要试图在 BD 中直接连 32 位的 AXI GPIO。应在 RTL 顶层（`top.v`）直接拆分为高低位（如 Low 32 + High 16），在 BD 中分别接双通道 GPIO。
  3. **Python API 掩码**：PYNQ 新版本中，`AxiGPIO.channel.write(data, mask)` 必须带掩码，写 32 位全位时填 `0xFFFFFFFF`。
  4. **48位有符号数还原**：Python 读回高低位拼接后，`(high << 32) | low` 得到的是无符号数。必须判断是否大于 \(2^{47}\)，大于则减去 \(2^{48}\) 才能得到真实的负数（补码还原）。
- **失效条件**：上述规则适用于 Zynq-7000 系列与 PYNQ 3.x 及以上版本。若不按掩码写入，硬件寄存器将不会被修改。

## 技能25：硬件状态位防冲突与强制复位

- **适用场景**：上位机控制 FPGA 时，需要在“自定义 RTL 扫频”和“官方音频闭环”两个模式间来回切换。
- **使用方法 / 踩坑清单**：
  1. **全局标志位**：引入 `_RTL_DESIGN_LOADED` 记录自定义 bitstream 是否已烧录，防止每次扫频都重烧。
  2. **冲突点**：调用官方音频驱动会加载 base.bit 重置 PL，但全局标志位仍为 `True`，切回 RTL 时会因寄存器不对而超时死机。
  3. **强制复位**：在初始化音频驱动（`force_reinit=True`）时，必须显式将 `_RTL_DESIGN_LOADED = False`。
- **验证方法**：RTL扫频 -> 切到Audio模式 -> 再切回 RTL 扫频，若无 `out_done 超时` 报错，则说明状态位复位成功。


## 五、测量与校准

## 技能26：积分窗长度会系统性改变测量结果（短窗低估高频）

- **适用场景**：扫频曲线在高频段"看起来像滤波器滚降"，但幅值随测量参数（积分周期数）变化；或换一版参数后曲线整体抬升/下沉。
- **使用方法 / 踩坑清单**：
  1. **先做"参数扫描"再下结论**：对同一个频点，用不同的积分周期数各测若干次，看幅值是否收敛。若随窗长单调变化，说明测到的是**偏差**而不是器件特性。
  2. **实测数据（本项目短接链路）**：20 kHz 处 `periods=20 → 14909`、`p=100 → 18252`、`p=400 → 18940`、`N=2500 → 19075`。用"每窗固定损失 k 个起始样本"建模，拟合得 `k ≈ 11.5` 个样本（≈0.24 ms），在 N=2441 时残差仅 0.04 dB。
  3. **修正方式**：把积分窗做长（本项目 20 kHz 用 400 个周期、N≈1000）。短窗的偏差在低频段可忽略（N 很大），所以**只在低频测同一组参数是发现不了的**。
  4. **对校准的影响**：若标定与测量使用相同的调度，该偏差会被校准吸收；但**原始曲线**会失真，且一旦调度改变，旧校准就失效。
- **失效条件**：若测量的信号本身不是严格周期的（或存在频率漂移），加长积分窗反而会引入相干损失，此时应改用多次短窗平均。

## 技能27：校准表的工程化——复数系数 + 元数据 + 原子写

- **适用场景**：测量系统需要一个可复现、可追溯、能被多个进程共享的校准表。
- **使用方法 / 设计规范**：
  1. **存复数系数而不是"增益 + 相位"两个独立标量**：`H_cal = mag_gain·e^{j·phase_offset}`，同时保留 `h_re/h_im` 与人读字段。去嵌入写成 `H_dut = H_meas · H_cal`，幅值按**对数**插值、相位按**增量**（`wrap(p1-p0)`）插值——这样跨 ±180° 不会错。
  2. **相位偏移按 mod 360 存储有边界风险**：单独存"相位偏移"再用线性插值，在回绕点会插出 180° 的错。复数表示没有这个问题，且对非网格频点更稳。
  3. **表里必须记录驱动条件**：`ref_amp`、`dac_volume`（数字音量寄存器值）、采样率、`sweep_id`、创建时间、备注。**改变驱动电平时整条幅频会整体平移**（本项目把 DAC 从 −12 dB 改到 −6 dB 会让旧表静默失效 6 dB），必须能检测出来并告警。
  4. **原子写**：先写 `path + ".tmp"`、`fsync`、再 `os.replace`。直接 `open(path,"w")` 在写入过程中崩溃会留下 **0 字节的表**，后续加载会抛异常，甚至让整个服务起不来。
  5. **加载容错 + 热重载**：空文件/坏 JSON 按空表处理（只告警，不抛异常）；记录 `(mtime, size)`，文件变化时自动重读。
- **失效条件**：若测量链路本身的相位不是"模 360"可描述（例如存在强非线性或多次谐波），复数单频校准不足以描述，需要按谐波建模。

## 技能28：校准相位"整体平移"的快速诊断法

- **适用场景**：已校准的短接（或已知直通）曲线本应是 0 dB / 0°，但相位从低频 0° 一路下坠到高频 −150°。
- **使用方法 / 踩坑清单**：
  1. **先看残差是不是"恒定延迟"**：对解缠后的相位残差求 `τ = −Δφ / (360·Δf)`。若 τ 在整个频段近似常数，就是**延迟**问题；若 τ 随频率变化，才是滤波器/相位响应问题。
  2. **对照"一个采样"**：本项目残差恒定 20.6 µs，而 `1/fs = 20.48 µs`——正好一个采样。这类"整数个采样"的偏差通常来自**窗口起点对齐**或**基准表与当前状态不一致**，而不是模拟电路。
  3. **排除硬件漂移**：同一时刻用多条路径测同一频点（例如网页端一次扫频、标定脚本新进程一次扫频、网页端再一次扫频）。若原始相位一致到 0.1° 以内，说明测量链稳定，问题在**软件缓存/基准表**。
  4. **检查"表是否真的被重新加载"**：很多实现只在内存表为空时加载一次，重建文件后进程仍用旧表——"校准后"等于"新测量 − 旧基准"，差值正好是被换掉的那部分。
- **失效条件**：若相位残差不是线性的（例如低频正常、中频突变），说明是滤波器或非线性环节，不能按延迟处理。

## 技能29：扫频数据落盘要同时保留原始值与校准值

- **适用场景**：需要事后回溯"当时是原始数据长什么样"，或要用真实数据重新拟合校准表。
- **使用方法 / 设计规范**：
  1. **列设计**：`mag_v_raw / mag_db_raw / phase_deg_raw / phase_valid`（未校准）与 `mag_db_cal / phase_deg_cal / cal_applied`（已校准）并存，另加 `sweep_id`、`timestamp`、`mode`。
  2. **必须能区分"已校准"与"未校准"**：用 `cal_applied` 标志位，而不是靠"数值看起来合理"来猜。
  3. **表头变更要归档旧文件**：新增列时把旧 CSV 改名为 `history.csv.<时间戳>.bak`，否则同一份文件里混用两种列宽，pandas/DictReader 会读成错位。
  4. **只允许"网页端主动扫频"写入历史**：脚本自身的标定扫频不要写历史，避免把不同目的的测量混在一起（可用临时表路径或独立输出）。
- **失效条件**：若历史文件需要被多个进程同时追加，建议按天分文件或加文件锁；本规范只保证单写者语义。

## 技能30：标定脚本应自带扫频，而不是依赖历史数据

- **适用场景**：需要重复标定（换夹具、换驱动电平、换环境），而历史数据可能不完整、混有其他目的的数据。
- **使用方法 / 设计规范**：
  1. **标定脚本自己加载设计并扫频**：调用与网页端相同的 `configure_codec + load_design` 路径，保证测量条件一致；标定数据不落历史。
  2. **扫频频点必须与测量频点一致**：本项目固定 240 点对数扫频（20 Hz~20 kHz），脚本与网页端共用同一套频率生成逻辑。
  3. **记录数据来源**：元数据里写 `source: "calibrate_path.py self-sweep"`、`sweep_id`、`repeat`、`periods`，便于事后追溯。
  4. **避免并发**：标定期间不要在网页端点扫频——两者会争用 PL 与 AXI 寄存器，且标定会重新加载 bitstream。
- **失效条件**：若板端无法自己扫频（例如只能通过上位机采集），则退化为"从文件导入"，但必须校验导入数据的驱动条件与测量条件。

## 技能31：多次扫频复数平均与一致性判据

- **适用场景**：单次扫频的噪声仍影响曲线平滑度，或需要判断某频点的测量是否可信。
- **使用方法 / 设计规范**：
  1. **按复数平均而不是分别平均幅值和相位**：`H = mean(mag_i·e^{j·phase_i})`，再取 `|H|` 与 `arg(H)`。分别平均会在相位噪声大时高估幅值。
  2. **同时输出一致性指标**：`coherence = |mean(H)| / mean(|H|)`，1 表示完全一致，接近 0 表示相位在乱跳；再配合幅值离散度（std/mean）。
  3. **用法**：`--repeat N` 指定次数；可用 `--min-coherence 0.98` 自动剔除不稳定频点。本项目 `--repeat 3` 时 coherence 中位数 1.0000、最小 0.9931。
  4. **注意时间成本**：重复 N 次就是 N 倍扫频时间，标定时可以多、日常测量时少。
- **失效条件**：若被测系统本身在漂移（温漂、接触不良），复数平均会把漂移"平均掉"并给出偏低的 coherence——此时应先解决稳定性，而不是加大平均次数。

## 技能32：频率-积分周期调度（恒定样本数）

- **适用场景**：扫频要在有限时间内兼顾低频与高频的稳定性，而"全频段固定周期数"或"全频段固定 FFT 点数"都不理想。
- **使用方法 / 设计规范**：
  1. **先分清两个量**：周期数 `periods` 与积分样本数 `N = periods·fs/f`。本项目实测发现决定稳定度的是 **N**（各频点稳到 cv≤0.15% 所需 N 都在 1000~2000），不是 `periods`。
  2. **单点耗时 ≈ periods/f**：低频一个周期就是几十毫秒，所以时间几乎全花在低频段。由此得到"每点积分时间恒定"的调度：
     `periods(f) = clamp(N_target·f/fs, p_min, p_max)`
  3. **下限 `p_min` 由低频决定**：20 Hz 处 `p=1 → 2.5%` 抖动、`p=2 → 0.22%`、`p=3 → 0.03%`；但扫频曲线的**逐点**抖动还受窗口划分影响，实测 `p=3/6/10/16 → 0.048/0.032/0.018/0.012 dB`，所以低频建议 `p_min ≥ 10`。
  4. **上限 `p_max` 由高频决定**：20 kHz 要 300~500 个周期（N≈1000~2000）才稳。
  5. **代价核算**：本项目 240 点、`N=1000/p_min=10` → 单轮约 19.5 s（实测 19.9 s）。
- **失效条件**：若采样率或频点密度改变，上述经验值需要重算；`p_min` 过高会让低频段占用过多时间，导致高频段 N 被迫下降。

## 技能33：测量脚本里的"超时保护"与"时长预算"是两件事

- **适用场景**：扫频脚本既要防止卡死，又要在资源受限时控制总时长。
- **使用方法 / 设计规范**：
  1. **超时保护**：给单轮扫频设硬上限（本项目 120 s），在**每个频点测完后**检查累计用时，超过立即抛异常并中止；中止时不要写任何结果文件（避免留下半张表）。
  2. **时长预算（可选）**：用来在"时间不够"时主动降精度（缩小积分窗）。它与超时保护的目的相反——一个是保底，一个是优化。
  3. **接负载后建议关掉预算**：真实负载可能让单次测量变慢，此时若预算仍在，调度会被自动压缩，导致曲线质量随负载变化而漂移。本项目最终把预算设为 0（不限制），只保留 120 s 超时保护，保证"调度固定、结果可比"。
  4. **预算收缩要有优先级**：先降低频段（最贵），再降 `N_target`；否则会出现"降了 N 仍然超时"的死循环。
- **失效条件**：如果板子也可能整体卡死（驱动死锁、总线下挂），单轮超时检查本身也可能被卡住，需要外部看门狗或进程级超时。

## 技能34：校准表热重载（文件指纹）

- **适用场景**：长时间运行的服务（网页后端、采集守护进程）需要在不重启的情况下使用新生成的校准表。
- **使用方法 / 设计规范**：
  1. **记录文件指纹**：加载时保存 `(mtime, size)`；每次使用前比对，变化则重读。
  2. **三种状态都要处理**：文件存在且未变 → 直接返回；文件变化 → 重读；文件被删除 → 清空内存表（回到未校准），不要继续用旧表。
  3. **读失败不阻断**：解析失败时沿用当前内存表并只告警一次，避免因为一次坏文件让整个服务不可用。
  4. **配合原子写**：只有配合"临时文件 + os.replace"，指纹判断才不会被"读到写了一半的文件"误导。
- **失效条件**：若校准表放在网络文件系统上，`mtime` 精度可能不足（秒级），极端情况下同一秒内的两次写入无法区分；此时可加内容哈希。

## 技能35：采样窗起点对齐——一个采样会造成 20 kHz 上百度的相位偏差

- **适用场景**：扫频相位在高频突然偏离模型 100° 以上，但低频基本正常；多次重启/多进程之间结果不一致；同一频点的幅值正常而相位像“整体转了一个角度”。
- **使用方法 / 踩坑清单**：
  1. **先算等效延迟**：对解缠后的相位残差拟合 `τ = −Δφ/(360·Δf)`。若 τ 近似常数且接近 `1/fs`，就是**整采样平移**，不是模拟电路。本项目 `fs = 100 MHz/2048 = 48828.125 Hz`，一个采样 **20.48 µs**；实测重启前后差约 **24 µs**（一个采样 + 3.5 µs 帧内偏移），在 20 kHz 正好是 **147°**（相位 = 360·f·τ）。
  2. **判断是“进程内”还是“跨进程”**：连续两次扫频（同一进程）重复性 ±0.1°，而重启后整体平移，说明进程内已对齐、跨进程未对齐。不要再用“平均多次”掩盖，平均消不掉常数相位。
  3. **RTL 对齐**：在 `top.v` 里把 `ps_start` 先锁存为 `start_pending`，等 `rx_data_valid`（I2S 帧有效）且状态机在 `IDLE` 时才真正启动：

     ```verilog
     wire start_here = start_pending && rx_data_valid && (state == IDLE);
     if (start_here) start_pending <= 0;
     else if (ps_start && state == IDLE) start_pending <= 1;
     ```

     这样启动点固定在“帧边界”，进程内重复性从“可能差一个采样”变成“稳定”。本项目改完后同进程 20 kHz 重复性 0.08°。
  4. **跨进程仍会差一个采样**：codec 的 DAC/ADC 帧相位在每次 `configure_codec + load_design` 后不一定相同。彻底解决要么把 I2S 帧计数器/codec 帧同步也纳入复位对齐，要么每次启动重测短接（见技能三十二），用当前进程的短接把相位重新锚定。
  5. **验证方法**：同一频点用“网页扫频 → 标定脚本新进程 → 网页扫频”三条路径对比原始相位；若三者一致到 0.1° 内，说明测量链稳定，问题只在“表与当前进程不匹配”。
- **失效条件**：若相位残差不是线性的（低频正常、中频突变），是滤波器/非线性，不是采样平移；若 `rx_data_valid` 本身抖动，锁存也可能锁到错误帧，需要示波器/ILA 看 I2S 帧边界。

## 技能36：启动参考扫频——把“当前进程的短接”自动测出来

- **适用场景**：每次重启 dashboard 后，直连校准表与当前进程的短接相位不一致，导致 20 kHz 相位错误；又不想每次手工跑 `calibrate_path.py`。
- **使用方法 / 设计规范**：
  1. **默认开启**：`run_dashboard.py` 里 `START_WITH_REFERENCE` 默认 `1`，只有显式 `START_WITH_REFERENCE=0` 才跳过；`start_dashboard.sh` 的默认值也改成 1。这样 `python3 run_dashboard.py` 直接启动就会触发。
  2. **主线程加载 PL**：pynq 的 `Overlay` 需要主线程的 asyncio loop，所以先在主线程 `_ensure_rtl_design()`（`configure_codec + load_design`），再起后台线程跑参考；否则会报 `There is no current event loop in thread 'Thread-1'`。
  3. **网页立即可用**：参考在后台跑，Flask 立即 `app.run()`；`/api/status` 返回 `reference.running`，前端把“开始扫频测量”按钮禁用并显示“正在进行相位对齐...”；`/api/start_sweep` 在参考期间返回 409 `{"status":"busy","msg":"正在进行相位对齐，请等待参考扫频完成后再试"}`。
  4. **一轮即可**：参考只扫一轮 240 点（`n_target=1000`，周期 10–410，约 20 s），不重复平均；它的目的是“相位锚点”，不是提高信噪比。
  5. **扫完才更新**：240 点先放在内存 `rows`，全部结束后才 `cal.CAL_TABLE = rows` + `save_calibration_table()`（临时文件 + `os.replace` 原子写）；中途失败（比如检测到不是短接）直接抛异常，旧表原封不动、按钮恢复。
  6. **自动 re-exec 到 venv**：系统 `python3` 没有 pynq 时，`run_dashboard.py` 顶部检测并 `os.execv` 到 `/usr/local/share/pynq-venv/bin/python3`，保证“project 目录下直接 `python3 run_dashboard.py`”也能跑。
- **失效条件**：若参考扫频本身被 DUT 挡住（不是短接），参考会按“前 5 点绝对判据”失败并保留旧表；此时要先换短接再启动。若进程在参考期间被 kill，下次启动仍需重新参考。

## 技能37：短接检测——绝对幅度比与“电平无关”判据的取舍

- **适用场景**：启动参考前需要判断“现在接的到底是不是短接”，避免把 DUT 当成短接写进校准表。
- **使用方法 / 踩坑清单**：
  1. **只用前 5 个频点（20–26 Hz）做绝对幅度判据**：`ratio = (mag · old_gain) / level_scale`，要求 `0.98 ~ 1.02`；串了 1 k/2.03 k/11.6 k/97.2 k 的 DUT 第一点就会以 0.916/0.844/0.486/0.100 被拦。
  2. **必须按 DAC 音量归一化**：codec 的音量 `0x402B/0x402C` 会从 `0x10`（−6 dB）变成 `0x08`（−12 dB），整体幅度差 2 倍。用 `app.py` 的 `_current_dac_volume()` 读出当前值，再和旧表 meta 里的 `dac_volume`（缺失时按 0x10）算 `level_scale = cur/old`，否则短接会被误判成 0.500。
  3. **20 Hz 相位不可靠**：20 Hz 正好在 codec 高通拐点，重启后短接自身相位会漂 3.48°；用 0.5° 门限会把短接误判。相位判据应放宽或删除，改用幅度。
  4. **20 kHz 形状判据也不可靠**：codec 高频在进程间会漂 1–2 dB，短接的 `mag(20k)/mag(20Hz)` 形状比会到 0.769（−2.2 dB），5%/20% 门限都可能误拦短接。最终方案是**只用前 5 点幅度**，20 kHz 形状判据删除。
  5. **纯电感是例外**：9.8 mH 的 DCR 仅约 12 Ω，20 Hz 的 H≈0.999，和短接只差 0.1%，前 5 点判据拦不住；这是该方法的固有限制，需要更细的绝对门限或高频判据才能区分。
- **失效条件**：若 DUT 在 20–26 Hz 的等效阻抗与短接差不到 2%（例如纯 9.8 mH），判据会放行；若 DAC 音量读数失败/为 None，`level_scale` 退回 1.0，仍可能误判。

## 技能38：H 平面表的“进程无关性”——短接会抵消，不要重建/旋转

- **适用场景**：每次新进程都要换一张 H 平面表，否则高频崩；怀疑“表必须和短接表配套”。
- **使用方法 / 设计规范**：
  1. **先认清公式**：`raw = S · H_true`，短接表就是 `S`，所以

     ```
     H_row = raw · 短接表 = H_true_row
     ```

     短接在表里**已经抵消**，H 平面表与“用哪张短接表建”无关，是**进程无关**的。
  2. **表崩的真正原因**：测量时用的短接表与**当前进程**不一致。`H_cal = raw · S_old = H_true · (S_cur/S_old)`，多了一个复比例，20 kHz 就偏 100° 以上。只要启动参考测出**当前进程**的短接，`H_cal = H_true`，旧表直接可用。
  3. **不要重建**：把旧表乘 `S_new/S_old` 会得到 `H_true_row · S_new/S_old`，反而把表转错（本项目 9.8 mH+11.6 k 的 20 kHz 被推到 −2.50 dB/−79°、−2.69 dB/−116°）。
  4. **不要旋转**：`apply_short_change` 再乘一次 `S_cur/S_ref` 是同一类错误（−2.70 dB/−116°）；正确做法是**什么都不做**，只保留启动参考。
  5. **验证**：短接参考 20k `5.347e-5/−86.12°` 与旧表建表短接 `5.348e-5/−86.06°` 一致时，9.8 mH+11.6 k 的 20 kHz 回到 **−6.28 dB/−3.14°**（模型 −6.28/−3.12°）。
- **失效条件**：若参考测得的是 DUT 而不是短接（前 5 点判据失效，例如纯 9.8 mH），H_cal 仍会带 DUT 的响应，表不可用；此时必须先确保接的是短接。

## 技能39：H 平面插值——复平面反距离加权，别用中值滤波

- **适用场景**：同一 |H| 下不同相位类型的 DUT（纯电阻 vs 容性 RC）在 6.6–6.9 kHz 出现假陷波；按幅度插值/中值滤波会破坏真实特征。
- **使用方法 / 设计规范**：
  1. **按复数 H 插值**：每条标准行存 `h_re/h_im`，在复平面算距离 `d = |H_cal − H_row|`，权重 `w = 1/(d² + 1e-6)`，加权平均 `Zin`。这样纯电阻和 RC 会各自取到相位匹配的标准行，不会在电平交叉处插错。
  2. **频率方向用 log f 线性插值**：`np.interp(log(f), log(F), row)`，240 点足够密。
  3. **不要中值滤波**：6.6–6.9 kHz 的“假陷波”是插值方式造成的，不是噪声；中值滤波会连真实谐振一起削掉。换成复平面 IDW 后陷波自然消失。
  4. **近短路保护**：`|H| > 0.999` 时直接返回原 H，避免 `Z = Zin(1-H)/H` 放大误差。
  5. **R_ref 从 97.2 kΩ 的低频 Z 取中位数**，约 10.98 kΩ；不要用标称 10 kΩ 或万用表值硬编码。
- **失效条件**：若 DUT 的 H 落在标准行覆盖不到的区域（例如很大的纯电感），IDW 只能近似；需要补标准件或改用物理模型。

## 技能40：标准件要用万用表值，不要用标称值

- **适用场景**：RC/RL 标准行拟合出的串联电阻与万用表差很多；曲线整体偏移。
- **使用方法 / 踩坑清单**：
  1. **先确认标准件本身**：本项目曾把 1.02 kΩ 当成 10 nF 的串联电阻，实际 DUT 并没有串 1.02 kΩ，导致 10 nF 拟合出 `R_s=1.08 kΩ` 的错误结论；换成 1.473 kΩ 实测后修正。
  2. **1.55 kΩ 实际是 15.5 kΩ**：扫频高频 −14.8 dB/−34.9° 的“异常”其实是电阻读错了一位；用万用表复核后重建。
  3. **RC 的 R 用万用表值**：10 nF+11.6 k 用 11.6 kΩ（万用表），不要用标称 11.6 k 的 ±5%；拟合容差会直接进入标准行。
  4. **RL 的 R 是“总电阻”**：9.8 mH 线圈的 DCR（约 12 Ω）+ 串联电阻，例如 9.8 mH+11.6 k 的 `Rtot=11612`；不要把 DCR 漏掉。
  5. **标准行的 `level` 用 |H| 中位数**，排序后建表；同一 DUT 重复测的 `level` 会因短接/音量轻微变化，但 H 的复形状稳定。
- **失效条件**：万用表本身精度（0.5% 级）会限制标准行精度；10 nF 电容容差（±5%~±10%）会限制 RC 行的相位精度，需要时用 LCR 表测。

## 技能41：直连校准表的工程化——复数、原子写、热重载、元数据

- **适用场景**：校准表被网页进程和标定脚本共享，需要可复现、可追溯、不半写。
- **使用方法 / 设计规范**：
  1. **存复数系数**：`h_re/h_im` 为主，`mag_gain/phase_offset_deg` 为人读字段；去嵌入用复数乘，幅值按对数插值、相位按增量插值，跨 ±180° 不错。
  2. **原子写**：`.tmp` + `fsync` + `os.replace`；直接 `open(path,"w")` 崩溃会留下 0 字节表，服务起不来。
  3. **热重载**：记录 `(mtime,size)`，文件变化自动重读；文件删除则清空内存表；解析失败沿用旧表并只告警一次。
  4. **元数据**：`dac_volume`、`ref_amp`、`created`、`source`、`freq_points`、`repeat`、`periods`；驱动电平变化时能告警/归一化。
  5. **原始值与校准值都落盘**：`mag_db_raw/phase_deg_raw` 与 `mag_db_cal/phase_deg_cal` 并存，加 `cal_applied` 标志；表头变更时旧 CSV 自动改名归档。
- **失效条件**：多进程同时追加历史需要文件锁或按天分文件；网络文件系统的 mtime 精度可能不够，需要内容哈希。

## 技能42：测量排错的总原则——先分“随机/系统”，再分“硬件/软件”

- **适用场景**：扫频曲线“看起来像器件特性”，但换参数/换进程就变；或者同一 DUT 多次测量不一致。
- **使用方法 / 踩坑清单**：
  1. **同点重复性**：同一频点连续测 N 次，看幅值 cv、相位 std。cv 大 → 随机（积分窗、信噪比）；cv 小但曲线整体偏 → 系统。
  2. **参数扫描**：改变 `periods`/`N`/`dac_volume`/`start` 对齐，看结果是否单调收敛；收敛到某值说明之前是偏差。
  3. **多路径对照**：网页扫频、标定脚本新进程、网页再次扫频，三条路径比原始相位；一致 → 测量链稳定，问题在表/缓存/进程。
  4. **先短接后 DUT**：任何“高频崩”先看短接本身是否 0 dB/0°；短接不正常时不要怀疑 DUT 或算法。
  5. **一次只改一个变量**：表、短接、音量、RTL、标准件分开验证；本项目多次因为同时换了短接表和 H 平面表，把问题归错到“旋转方向”。
- **失效条件**：若 DUT 本身在漂移（温漂、接触电阻），重复性实验会把漂移误判成随机；需要先固定夹具/等待热稳定。

## 技能43：正交解调定点归一化与四态校准规范

- **适用场景**：把 FPGA 解调器输出的 48 位整数累加值还原为物理幅值（V）与相位（度），并对整机增益/相位偏差做系统级校准。
- **使用方法 / 设计规范**：
  1. **归一化口径唯一**：`norm_factor = N × ADC_GAIN × LO_GAIN`，`I = acc_I × 2 / norm_factor`。系数必须与 Python 定点模型**单点同步**——模型改 N，驱动必须同步修改，否则幅值系统性失真。
  2. **幅值相位公式**：`mag = hypot(I, Q)`，`phase = degrees(atan2(Q, I))`；满量程电压单独定义常量（`ADC_FULL_SCALE_V`），把归一化幅值换算成 V。
  3. **四态校准**：每个频点用 4 个已知参考态（如幅值 A_ref、相位 0/90/180/270°）实测，`mag_gain = A_ref / mean(mag)`、`phase_offset = 平均回绕相位差`。
- **失效条件**：N 与硬件实际积分窗口不一致时还原幅值系统性偏大；跳过四态校准直接读数，会带入固定的增益与相位偏差且难以排查。


## 六、上位机、部署与可视化

## 技能44：Flask + Plotly 轻量级上位机仪表盘搭建规范

- **适用场景**：在开发“便携式电路诊断系统”时，需要一个能在局域网/本地离线运行、且能动态刷新 Bode 图的前端界面。
- **核心设计规范**：
  1. **离线依赖**：绝不能直接在 HTML 里写 CDN 链接。必须将 `plotly-2.35.2.min.js` 下载到本地 `static/` 目录下引入，保证拔掉网线也能跑。
  2. **前后端分离**：使用 Flask 仅提供两个路由：`/` 返回 HTML 页面；`/api/sweep/latest` 返回 JSON 格式的假数据（Mock Data）或硬件推来的真数据。
  3. **动态重绘**：前端 JS 使用 `Plotly.react()` 而不是 `Plotly.newPlot()`，在点击“刷新”或轮询硬件数据时，可平滑更新曲线而不闪烁。
- **验证方法**：运行 `python app.py`，浏览器访问 `http://127.0.0.1:5000`，能看到带数据点、坐标为对数轴（Log）的幅频与相频曲线。

## 技能45：PYNQ 局域网共享与静态 IP 配置规范

- **适用场景**：PYNQ 板子直连电脑并通过电脑（如手机热点）共享网络，或通过路由器连接局域网，需要给板子配置固定 IP 以访问网页。
- **踩坑清单**：
  1. **Windows 共享（ICS）失效**：在电脑的“网络连接”里，把外网网卡（如 WLAN）属性切到“共享”，勾选“允许其他网络用户连接”并指向以太网卡。若没反应，去 `services.msc` 强制启动 `Internet Connection Sharing (ICS)` 服务。
  2. **网段冲突**：开启共享后，Windows 常会把电脑以太网卡 IP 强制变成 `192.168.137.1`。必须把板子 IP 设在同一网段（如 `192.168.137.99`），否则物理通但逻辑不通。
  3. **DNS 丢失**：Linux 板子配好静态 IP 后，务必手动写入 DNS，否则 `ping 8.8.8.8` 能通，但 `pip` 下载会报 `Temporary failure in name resolution`。
- **验证方法**：在板子终端 `ping -c 3 www.baidu.com` 若返回时间而非错误，且 `/etc/resolv.conf` 中写入了 `nameserver 8.8.8.8`，即为成功。
- **失效条件**：板子断电重启后，手动敲的 `ifconfig` 和 `route` 命令会失效，需重新配置或写入自启脚本。

## 技能46：板端部署与 Git 推送的取证流程

- **适用场景**：需要把 Python/JSON/XSA 部署到 PYNQ 板，并确认 GitHub 远端与本地一致。
- **使用方法 / 踩坑清单**：
  1. **文本与二进制分开传**：文本走 Jupyter contents API 的 `format=text`；XSA/二进制走 `format=base64`（`upload_bin.py`）。直接 `cat` 大文件会截断。
  2. **Jupyter 根目录不是 `/`**：`/tmp/xxx.json` 会 404；路径要写 `project/data/...`（相对 `/home/xilinx/jupyter_notebooks`）。
  3. **部署后校验 sha256**：本地/远端逐文件比对（`verify_board_files.py`），不要只看“上传成功”。
  4. **GitHub 推送**：网络不通时用 SSH 443 包装（`ssh_us.cmd`：`140.82.112.36:443` + `HostKeyAlias=ssh.github.com`）；`git push` 报 `Connection timed out` 可重试，成功后 `git ls-remote` 仍可能超时，以 push 输出为准。
  5. **GitHub API 抓取有 100 KB 截断**：`web_fetch` 的 raw/contents 大文件会被截断，校验大文件要靠本地 sha256 或分段抓取。
- **失效条件**：板端无外网/DNS 时只能走局域网 Jupyter；XSA 的 base64 上传对大小敏感，超大文件建议分块。

## 技能47：Flask + PYNQ 的启动顺序——PL 必须在主线程加载

- **适用场景**：dashboard 后台线程加载 PL 报 `There is no current event loop in thread`；或网页起来后第一次扫频才加载 bitstream，导致第一次测量失败。
- **使用方法 / 设计规范**：
  1. **主线程加载**：`_ensure_rtl_design()`（`acceptance.configure_codec()` + `load_design(ensure_bitstream(), 1e8)`）在 `app.run()` 之前、主线程执行；后台线程只做扫频。
  2. **Flask 单线程**：`app.run(host="0.0.0.0", port=5000, debug=False, threaded=False)`，避免多请求并发争用 MMIO/PL。
  3. **启动即参考**：参考线程 daemon 化，主线程继续 `app.run()`；网页轮询 `/api/status` 拿 `reference.running/done/error`。
  4. **venv re-exec**：系统 python 没有 pynq 时自动 `os.execv` 到 pynq venv；`XILINX_XRT=/usr` 要在 import pynq 前设置。
  5. **脚本/服务路径**：`start_dashboard.sh` 用 `sudo env XILINX_XRT=/usr ... /usr/local/share/pynq-venv/bin/python3 run_dashboard.py`；直接 `python3 run_dashboard.py` 由 re-exec 兜底。
- **失效条件**：若多个进程同时加载 bitstream/争用 `/dev/mem`，会出现 `Resource busy`；需要先 `pkill` 旧 dashboard 再启动。


## 七、数据与机器学习

## 技能48：机器学习防“数据泄漏”与域外测试规范

- **适用场景**：手头同时有“理想数学合成数据”和“少量真实硬件测试数据”，需要训练和评估 AI 模型。
- **使用方法 / 踩坑清单**：
  1. **绝对禁止混合训练**：真实数据存在底噪等域偏移，混入训练集会导致模型决策边界扭曲，把不知名的数据全判给真实类。
  2. **域外测试 (OOD)**：必须使用大量完美的合成数据训练模型，然后将真实硬件采集的 CSV 单独丢给模型做纯推理（不参与训练），观察其置信度。
- **验证方法**：在模型报告中明确区分“训练集准确率”和“真实数据域外测试结果”，且必须打印真实数据被分成了哪类。

## 技能49：AI 训练报告的“诚实性”声明规范

- **适用场景**：向导师或答辩评委展示 ML 训练报告时，防止用仿真数据冒充真实实测，保证学术严谨。
- **使用方法 / 踩坑清单**：
  1. **引入显式开关**：在训练脚本中增加 `--real` 参数。如果不传此参数，报告标题强制输出 `(dry-run 仿真)`；只有显式声明，才允许标“实测检验”。
  2. **免责声明**：必须在报告中写一句“理想合成数据易达极高准确率，该数字不代表真实硬件泛化表现”。
- **验证方法**：不带参数运行，报告自动降级为 dry-run 标题；带 `--real` 运行，标题变为实测检验。

## 技能50：频域特征提取中的相位解卷绕 (Phase Unwrap)

- **适用场景**：从扫频仪/FPGA 采回的 Bode 图数据中，提取“相位跨度”等特征供 AI 使用时。
- **使用方法 / 踩坑清单**：
  1. **相位跳变**：系统输出相位通常限制在 `[-180°, 180°]`，穿过 -180° 时会发生跳变，直接求跨度会导致数值假性爆炸。
  2. **解卷绕修复**：使用 `numpy` 的 `np.unwrap` 函数：`phase_unwrapped = np.degrees(np.unwrap(np.radians(phase_deg)))`，让曲线平滑连续。
- **验证方法**：画出解卷绕后的曲线，原本瞬间跳变 -180° 的断层，会平滑过渡为一条连续下降的曲线。
