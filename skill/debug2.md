## 技能二十二：积分窗长度会系统性改变测量结果（短窗低估高频）

- **适用场景**：扫频曲线在高频段"看起来像滤波器滚降"，但幅值随测量参数（积分周期数）变化；或换一版参数后曲线整体抬升/下沉。
- **使用方法 / 踩坑清单**：
  1. **先做"参数扫描"再下结论**：对同一个频点，用不同的积分周期数各测若干次，看幅值是否收敛。若随窗长单调变化，说明测到的是**偏差**而不是器件特性。
  2. **实测数据（本项目短接链路）**：20 kHz 处 `periods=20 → 14909`、`p=100 → 18252`、`p=400 → 18940`、`N=2500 → 19075`。用"每窗固定损失 k 个起始样本"建模，拟合得 `k ≈ 11.5` 个样本（≈0.24 ms），在 N=2441 时残差仅 0.04 dB。
  3. **修正方式**：把积分窗做长（本项目 20 kHz 用 400 个周期、N≈1000）。短窗的偏差在低频段可忽略（N 很大），所以**只在低频测同一组参数是发现不了的**。
  4. **对校准的影响**：若标定与测量使用相同的调度，该偏差会被校准吸收；但**原始曲线**会失真，且一旦调度改变，旧校准就失效。
- **失效条件**：若测量的信号本身不是严格周期的（或存在频率漂移），加长积分窗反而会引入相干损失，此时应改用多次短窗平均。

## 技能二十三：校准表的工程化——复数系数 + 元数据 + 原子写

- **适用场景**：测量系统需要一个可复现、可追溯、能被多个进程共享的校准表。
- **使用方法 / 设计规范**：
  1. **存复数系数而不是"增益 + 相位"两个独立标量**：`H_cal = mag_gain·e^{j·phase_offset}`，同时保留 `h_re/h_im` 与人读字段。去嵌入写成 `H_dut = H_meas · H_cal`，幅值按**对数**插值、相位按**增量**（`wrap(p1-p0)`）插值——这样跨 ±180° 不会错。
  2. **相位偏移按 mod 360 存储有边界风险**：单独存"相位偏移"再用线性插值，在回绕点会插出 180° 的错。复数表示没有这个问题，且对非网格频点更稳。
  3. **表里必须记录驱动条件**：`ref_amp`、`dac_volume`（数字音量寄存器值）、采样率、`sweep_id`、创建时间、备注。**改变驱动电平时整条幅频会整体平移**（本项目把 DAC 从 −12 dB 改到 −6 dB 会让旧表静默失效 6 dB），必须能检测出来并告警。
  4. **原子写**：先写 `path + ".tmp"`、`fsync`、再 `os.replace`。直接 `open(path,"w")` 在写入过程中崩溃会留下 **0 字节的表**，后续加载会抛异常，甚至让整个服务起不来。
  5. **加载容错 + 热重载**：空文件/坏 JSON 按空表处理（只告警，不抛异常）；记录 `(mtime, size)`，文件变化时自动重读。
- **失效条件**：若测量链路本身的相位不是"模 360"可描述（例如存在强非线性或多次谐波），复数单频校准不足以描述，需要按谐波建模。

## 技能二十四：校准相位"整体平移"的快速诊断法

- **适用场景**：已校准的短接（或已知直通）曲线本应是 0 dB / 0°，但相位从低频 0° 一路下坠到高频 −150°。
- **使用方法 / 踩坑清单**：
  1. **先看残差是不是"恒定延迟"**：对解缠后的相位残差求 `τ = −Δφ / (360·Δf)`。若 τ 在整个频段近似常数，就是**延迟**问题；若 τ 随频率变化，才是滤波器/相位响应问题。
  2. **对照"一个采样"**：本项目残差恒定 20.6 µs，而 `1/fs = 20.48 µs`——正好一个采样。这类"整数个采样"的偏差通常来自**窗口起点对齐**或**基准表与当前状态不一致**，而不是模拟电路。
  3. **排除硬件漂移**：同一时刻用多条路径测同一频点（例如网页端一次扫频、标定脚本新进程一次扫频、网页端再一次扫频）。若原始相位一致到 0.1° 以内，说明测量链稳定，问题在**软件缓存/基准表**。
  4. **检查"表是否真的被重新加载"**：很多实现只在内存表为空时加载一次，重建文件后进程仍用旧表——"校准后"等于"新测量 − 旧基准"，差值正好是被换掉的那部分。
- **失效条件**：若相位残差不是线性的（例如低频正常、中频突变），说明是滤波器或非线性环节，不能按延迟处理。

## 技能二十五：扫频数据落盘要同时保留原始值与校准值

- **适用场景**：需要事后回溯"当时是原始数据长什么样"，或要用真实数据重新拟合校准表。
- **使用方法 / 设计规范**：
  1. **列设计**：`mag_v_raw / mag_db_raw / phase_deg_raw / phase_valid`（未校准）与 `mag_db_cal / phase_deg_cal / cal_applied`（已校准）并存，另加 `sweep_id`、`timestamp`、`mode`。
  2. **必须能区分"已校准"与"未校准"**：用 `cal_applied` 标志位，而不是靠"数值看起来合理"来猜。
  3. **表头变更要归档旧文件**：新增列时把旧 CSV 改名为 `history.csv.<时间戳>.bak`，否则同一份文件里混用两种列宽，pandas/DictReader 会读成错位。
  4. **只允许"网页端主动扫频"写入历史**：脚本自身的标定扫频不要写历史，避免把不同目的的测量混在一起（可用临时表路径或独立输出）。
- **失效条件**：若历史文件需要被多个进程同时追加，建议按天分文件或加文件锁；本规范只保证单写者语义。

## 技能二十六：标定脚本应自带扫频，而不是依赖历史数据

- **适用场景**：需要重复标定（换夹具、换驱动电平、换环境），而历史数据可能不完整、混有其他目的的数据。
- **使用方法 / 设计规范**：
  1. **标定脚本自己加载设计并扫频**：调用与网页端相同的 `configure_codec + load_design` 路径，保证测量条件一致；标定数据不落历史。
  2. **扫频频点必须与测量频点一致**：本项目固定 240 点对数扫频（20 Hz~20 kHz），脚本与网页端共用同一套频率生成逻辑。
  3. **记录数据来源**：元数据里写 `source: "calibrate_path.py self-sweep"`、`sweep_id`、`repeat`、`periods`，便于事后追溯。
  4. **避免并发**：标定期间不要在网页端点扫频——两者会争用 PL 与 AXI 寄存器，且标定会重新加载 bitstream。
- **失效条件**：若板端无法自己扫频（例如只能通过上位机采集），则退化为"从文件导入"，但必须校验导入数据的驱动条件与测量条件。

## 技能二十七：多次扫频复数平均与一致性判据

- **适用场景**：单次扫频的噪声仍影响曲线平滑度，或需要判断某频点的测量是否可信。
- **使用方法 / 设计规范**：
  1. **按复数平均而不是分别平均幅值和相位**：`H = mean(mag_i·e^{j·phase_i})`，再取 `|H|` 与 `arg(H)`。分别平均会在相位噪声大时高估幅值。
  2. **同时输出一致性指标**：`coherence = |mean(H)| / mean(|H|)`，1 表示完全一致，接近 0 表示相位在乱跳；再配合幅值离散度（std/mean）。
  3. **用法**：`--repeat N` 指定次数；可用 `--min-coherence 0.98` 自动剔除不稳定频点。本项目 `--repeat 3` 时 coherence 中位数 1.0000、最小 0.9931。
  4. **注意时间成本**：重复 N 次就是 N 倍扫频时间，标定时可以多、日常测量时少。
- **失效条件**：若被测系统本身在漂移（温漂、接触不良），复数平均会把漂移"平均掉"并给出偏低的 coherence——此时应先解决稳定性，而不是加大平均次数。

## 技能二十八：频率-积分周期调度（恒定样本数）

- **适用场景**：扫频要在有限时间内兼顾低频与高频的稳定性，而"全频段固定周期数"或"全频段固定 FFT 点数"都不理想。
- **使用方法 / 设计规范**：
  1. **先分清两个量**：周期数 `periods` 与积分样本数 `N = periods·fs/f`。本项目实测发现决定稳定度的是 **N**（各频点稳到 cv≤0.15% 所需 N 都在 1000~2000），不是 `periods`。
  2. **单点耗时 ≈ periods/f**：低频一个周期就是几十毫秒，所以时间几乎全花在低频段。由此得到"每点积分时间恒定"的调度：
     `periods(f) = clamp(N_target·f/fs, p_min, p_max)`
  3. **下限 `p_min` 由低频决定**：20 Hz 处 `p=1 → 2.5%` 抖动、`p=2 → 0.22%`、`p=3 → 0.03%`；但扫频曲线的**逐点**抖动还受窗口划分影响，实测 `p=3/6/10/16 → 0.048/0.032/0.018/0.012 dB`，所以低频建议 `p_min ≥ 10`。
  4. **上限 `p_max` 由高频决定**：20 kHz 要 300~500 个周期（N≈1000~2000）才稳。
  5. **代价核算**：本项目 240 点、`N=1000/p_min=10` → 单轮约 19.5 s（实测 19.9 s）。
- **失效条件**：若采样率或频点密度改变，上述经验值需要重算；`p_min` 过高会让低频段占用过多时间，导致高频段 N 被迫下降。

## 技能二十九：测量脚本里的"超时保护"与"时长预算"是两件事

- **适用场景**：扫频脚本既要防止卡死，又要在资源受限时控制总时长。
- **使用方法 / 设计规范**：
  1. **超时保护**：给单轮扫频设硬上限（本项目 120 s），在**每个频点测完后**检查累计用时，超过立即抛异常并中止；中止时不要写任何结果文件（避免留下半张表）。
  2. **时长预算（可选）**：用来在"时间不够"时主动降精度（缩小积分窗）。它与超时保护的目的相反——一个是保底，一个是优化。
  3. **接负载后建议关掉预算**：真实负载可能让单次测量变慢，此时若预算仍在，调度会被自动压缩，导致曲线质量随负载变化而漂移。本项目最终把预算设为 0（不限制），只保留 120 s 超时保护，保证"调度固定、结果可比"。
  4. **预算收缩要有优先级**：先降低频段（最贵），再降 `N_target`；否则会出现"降了 N 仍然超时"的死循环。
- **失效条件**：如果板子也可能整体卡死（驱动死锁、总线下挂），单轮超时检查本身也可能被卡住，需要外部看门狗或进程级超时。

## 技能三十：校准表热重载（文件指纹）

- **适用场景**：长时间运行的服务（网页后端、采集守护进程）需要在不重启的情况下使用新生成的校准表。
- **使用方法 / 设计规范**：
  1. **记录文件指纹**：加载时保存 `(mtime, size)`；每次使用前比对，变化则重读。
  2. **三种状态都要处理**：文件存在且未变 → 直接返回；文件变化 → 重读；文件被删除 → 清空内存表（回到未校准），不要继续用旧表。
  3. **读失败不阻断**：解析失败时沿用当前内存表并只告警一次，避免因为一次坏文件让整个服务不可用。
  4. **配合原子写**：只有配合"临时文件 + os.replace"，指纹判断才不会被"读到写了一半的文件"误导。
- **失效条件**：若校准表放在网络文件系统上，`mtime` 精度可能不足（秒级），极端情况下同一秒内的两次写入无法区分；此时可加内容哈希。
